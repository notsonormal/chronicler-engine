# Map: Prompt flexibility

Labels: wayfinder:map

## Destination

Every part of every story and state LLM call is decided: an author can change it through `data/` JSON or the existing UI, or it is a written engine rule with its reason. How a fixed test setup runs through Autoplay and what its reading pack holds is decided, and a prototype has made one reading pack on the current engine, so two setups can be compared. The engine changes are made, and a trial checks each one.

## Notes

- **Origin.** The real-LLM UI pass of the Autoplay review fixes (2026-10-22) showed faults in the prompts. Most of them sit in the parts of a call that the engine fixes in code, not in the preset text. Autoplay is the first tool that makes a long story with no player, so it is the first way to test the prompts. Evidence: [story transcript](assets/autoplay-story-transcript.md), [the stored Impersonate prompt of Input #93](assets/impersonate-prompt-157.txt), [the review of the Impersonate output](assets/impersonate-output-review.md).
- **Two kinds of work.** This map is the engine work: make every part of a prompt changeable, and make trials possible. The authoring of World data, cards and presets is a second effort that uses this tool.
- **Scope of the calls (owner, charting).** All story and state calls: the Narrator role (Narration, Event Narration, the regenerate of a user Input, Impersonate), the Quantifier and Options. The connection test is not in scope.
- **"Changeable" (owner, charting).** An author can change it in `data/` JSON or in the existing UI. A new UI is not part of this map.
- **ST and ME (owner, charting).** SillyTavern and Marinara Engine are a reference: we read their source and their default prompts. A live run of either app is not decided (see [Decide whether to run ST and ME live](issues/11-live-run-of-st-and-me.md)). Pinned commits: SillyTavern `06bde939fb1e9c4c8d8641d810f0a916b5bce127`, Marinara Engine `457e827a3d3291be978121f8c50c98c5dd9d644d`. Clone them outside the repo (for example `/tmp/research/`).
- **Judging (owner, charting).** It is too early to define what a good output is. In this map a comparison gives the owner a reading pack: the transcripts and the prompt of each call, side by side. The long-term direction is an LLM judge that sorts and an owner who decides.
- **Known engine defects wait (owner, plan review).** An empty `<PlayerInput>` block is the last text of the Impersonate call. [Decide which parts of a Narrator-role call an author can change](issues/06-the-layout-model.md) decided the fix: an empty layer renders nothing. [Decide the parameters of each call](issues/07-call-parameters.md) removed the global `response_length`, which reached Impersonate. The first trial prototype runs on the current engine and shows both.
- **Caching (owner, after charting).** A balance, not a goal. A roleplay call uses far fewer tokens than a coding agent, so the engine looks for cheap rules that stop a cache break on every call, not for the best hit rate. See [Find how prompt caching works for our providers and our layout](issues/12-prompt-caching.md).
- **Long-term memory and state (owner).** Needed for long play and Autoplay, but a new effort designs them ([seed](../long-term-memory-and-state/idea.md)). This map only keeps room: see [Decide whether this map designs memory and state, or only keeps room for them](issues/16-memory-and-state-scope.md).
- **Names.** No `CONTEXT.md` changes for now (owner, charting). One exception: ticket 21 adds the term **Connection slot** (owner, 2026-10-31, O6 in ticket 17). "Test setup" and "trial" are working names only: a test setup is a fixed World, Persona, opening, presets, connections and number of cycles; a trial is one execution of it through Autoplay.
- **Existing references. Start from these; do not redo them.** `docs/external_applications/` (`sillytavern_prompt_system.md`, `marinara_engine.md` with its "Game Mode Prompt Architecture", `marinara_engine_system_prompt.md`), `.scratch/_closed/steering-and-guided-generation/research/03-sillytavern-core.md`, and the engine rules that already have a written reason in `docs/diataxis/explanation/prompt_system_design.md` (system and user halves, the style and format sections after the history, XML tags as content labels, two tiers of NPC cards).
- **Skills.** `/grilling` for grilling tickets, `/research` for research tickets, `/prototype` for the prototype ticket. Read `docs/diataxis/reference/narrative/prompt_system.md` and `docs/diataxis/explanation/prompt_system_design.md` first.
- **Engine tickets (owner, 2026-10-31).** The engine changes are task tickets in this map, not a plan in `docs/plans/`. Each one is test first (`/tdd`), on its own branch, and ends with a passing `python build.py`. A new unit test goes only where `tests/STRATEGY.md` ("The one rule") allows it. A migration takes the next free step, adds a column with `ALTER TABLE … ADD COLUMN` guarded by `column_exists`, never edits an old `CREATE TABLE`, raises `LATEST_VERSION`, and gets its test in `plumbing_tests.rs`. Each ticket changes the docs that its change makes wrong (`docs/AGENTS.md`, "Direction of edits"). A Diátaxis doc states no plan and no value.
- **Standing rules.** Execution is in this map (owner, 2026-10-31): the map ends when the engine tickets are done. The owner wants plans written directly in the repo, not through Plannotator. Any new API takes a `GameId` and adds no read of `ActiveGame` (per-tab rule from the Autoplay work).

## Decisions so far

- [List what reaches the model in each call](issues/01-what-reaches-the-model.md) — each call sends one system and one user message with `max_tokens` and no sampler; tags, labels, frame sentences and history cuts are fixed in code; `response_length`, connection `max_tokens` and the option count (3) have no author handle; four rows of `prompt_system.md` contradict the code.
- [How ST and ME let an author change a call](issues/02-st-me-prompt-configuration.md) — both apps give an author the text, order, role and history depth of each part, per preset and per chat; neither exposes token-budget maths; ST sends the impersonation prompt as a trailing `system` message, ME as a trailing `user` message; 32 stale statements in `docs/external_applications/` are listed for the build plan.
- [Find the tools that evaluate characters and prompts](issues/05-evaluation-tools.md) — card evaluators (CardRefinery, CardQualifier), per-reply judges (ST-jeved, ME's Continuity Checker and Prose Guardian) and roleplay benchmarks exist; no tool scores a whole multi-cycle story.
- [Put the original ST cards in the repo](issues/03-place-the-original-cards.md) — five V2 cards (no V3, no Persona card, no separate lorebook) and their raw JSON are in `assets/source_cards/`; each card embeds its own lorebook; the Persona "father" error came from our conversion.
- [Compare our card and World format with ST and ME](issues/04-card-and-world-format.md) — we keep 4 card text fields; `first_mes` sits in an unused `example_dialogue`; `mes_example`, greetings, card system and post-history text, depth prompt and the lorebooks are dropped (lore became always-on `global_rules`); the conversion cut half of each description, including four "never speak for {{user}}" rules; the "father" error is in two Persona fields.
- [Find how ST, ME and other tools keep long-term state](issues/14-long-term-state.md) — ME is the shape to copy: a second call after each reply writes typed JSON into one row per Message and Swipe, placed near the newest history; ST core has only chat variables and World Info timed effects, and its trackers are third-party copies of the ME shape; a card change needs a person's approval and a version; Game 6 records 3 of 11 visible state changes. (Its claim that a failed Quantifier clears the Characters present was wrong; see the next ticket.)
- [Find how prompt caching works for our providers and our layout](issues/12-prompt-caching.md) — our layout breaks the cache on every call (shared prefix about 28%), because the card order is random (a `HashMap`), the presence marks change, and `GameState` comes first; cheap rules lift it to about 85%, and a history cut that moves in steps keeps a long trial cached; a 100-cycle trial costs about $2 with no cache; the OpenRouter host changes the price by up to 3.3 times.
- [Find how ST, ME and other tools keep long-term memory](issues/13-long-term-memory.md) — no stored story reaches the history cut; this World's prose passes the 64000-character cap at about cycle 39, or about cycle 10 at the engine's 8192-token Ollama default; ME is the only production tool with a memory for each Character (an audience list and first-person recollections, Swipe-pinned); ST keeps one summary per chat; one cheap call per scene is the cheapest workable shape, and memory text always sits under a cap.
- [Shape the test setup and the trial](issues/08-test-setup-and-trial.md) — a kept script runs a setup file through Autoplay on a probe server, with no engine change; it copies the 50-row `llm_messages` debug record while it runs; OpenCode Go with a token limit (about 3 M tokens for 100 cycles); a `content_filter` stop is restarted up to 5 times; one trial per setup now, 2 when comparing; same sampling as play, with a fixed card order; the prototype's reading pack is the shape. Two trials stopped at cycle 34 and 88; the first history cut came at cycle 39.
- [Decide the parameters of each call](issues/07-call-parameters.md) — match ME: `max_tokens` and samplers (typed `temperature`, `top_p`, plus a guarded free object) go on each preset, and the connection keeps the model, the host and a `max_tokens` ceiling; four connection slots (Narration, Impersonate, Quantifier, Options); the global `response_length` is removed; every OpenRouter call sends a `session_id` from the `GameId`; no override for each Game and no cache setting.
- [Decide what the state does when a state writer fails](issues/15-failed-state-writer.md) — keep: a failed state writer leaves the previous Room and Characters present, and the Job continues; this is already true for a model failure, and only the `Err` path of the runner clears them; 2 attempts stay; the banner becomes "keeping the Room and the Characters present"; every future state writer uses the same rule; the fix goes in the build plan. Game 6's 24 failures came from `gpt-4o-mini` on Azure, not OpenCode Go.
- [Decide whether this map designs memory and state, or only keeps room for them](issues/16-memory-and-state-scope.md) — keep room, design in a new effort; the layout has an open list of block types and no fixed place for a new block; the stepped history cut is one explicit step that knows what it dropped (the future compaction point); no new hook, no empty slot, no `SwipeState` change; story memory and state are pinned to the Swipe.
- [Decide which parts of a Narrator-role call an author can change](issues/06-the-layout-model.md) — faults only: the layout stays an engine rule until a trial shows a change helps the output or the cache; the build plan sorts both card lists by id, makes the history cut a stepped explicit step, renders nothing for an empty layer (the empty `<PlayerInput>`), and renames `Context:` to `Scenario:`; six layout changes wait for trials.
- [Decide which parts of a Quantifier or Options call an author can change](issues/10-quantifier-options-layout.md) — the same basis as the Narrator-role layout (faults only); `<LatestNarration>` becomes `<LatestMessage>` with no label, and it stays a separate block (cache is equal, and ME splits the same way); card text renders `{{user}}`; every card list is sorted by id; the Options count comes from a new `option_count` field on the Options preset (default 3), and the engine text names no count; the window of 4, the closing sentences and the answer format in the preset stay as they are.
- [Write the build plan for the engine changes](issues/09-build-plan.md) — the owner turned the plan into seven task tickets, grouped by purpose: the trial script first, then the prompt text, the history cut in blocks, the connection slots, the preset call parameters, the failed state writer and the doc corrections. Each ticket holds its own choices and its own check, and each passed a plan review.
- [Settle the open questions of the engine tickets](issues/17-settle-engine-questions.md) — the owner kept every recommended answer: a failed or missing state writer keeps the state, with no banner for the `Err` path; no route sets the Impersonate or Options slot yet; the fallback sentences stay; the Connection `max_tokens` value is a cap; and `CONTEXT.md` gets a **Connection slot** entry.

## Not yet specified

- **The criteria and the judge.** What makes an output good, and how an LLM judge sorts trials for the owner. A comparison of two setups waits for it (2 trials for each setup). Real trial transcripts now exist (`tmp/pf08/`, see [the trial prototype](assets/trial-prototype.md)); [Find the tools that evaluate characters and prompts](issues/05-evaluation-tools.md) is resolved. Open: every tool found judges one reply, so a check across replies (repetition, voice drift over the cycles of a trial) may be new work.
- **The layout trials.** Six layout changes that a trial must test, in a sequence still to set: no presence marks, `GameState` after the history, `example_dialogue`, author-editable instruction sentences, the history as chat messages, an author block order. How a trial runs one is now known ([Write the build plan for the engine changes](issues/09-build-plan.md)): a code branch, run on a second probe server with the same setup file, then `compare`. The sequence still waits for the criteria and the judge. See [Decide which parts of a Narrator-role call an author can change](issues/06-the-layout-model.md).
- **A UI for the new changeable fields.** The engine tickets add fields that only `data/` JSON can set. Known now: the Impersonate and Options connection pickers, the parameter fields of a preset (see [Decide the parameters of each call](issues/07-call-parameters.md)), and the `option_count` field of the Options preset (see [Decide which parts of a Quantifier or Options call an author can change](issues/10-quantifier-options-layout.md)). [Add the connection slots and remove the global response length](issues/21-connection-slots-and-response-length.md) adds no route for the two new slots (O3 in [Settle the open questions of the engine tickets](issues/17-settle-engine-questions.md)). Until this item lands, those slots and the new preset fields reach an existing database only through a new preset id or a new database. A Role for Impersonate, so its health shows apart from the Narrator, may belong here too.

- **The OpenCode Go input filter.** On OpenCode Go, a few calls fail with `content_filter` and `prompt_tokens: 0` on harmless text (4 of 178 Quantifier calls in trial B, and the Impersonate call that ended each trial). The trigger is unknown. If the restart limit of the trial does not hold, this becomes a ticket: replay a failed call and remove parts until it passes. See [Decide what the state does when a state writer fails](issues/15-failed-state-writer.md).

## Out of scope

- The authoring of the World, the cards and the presets: the "father" error in the Persona card, the wording of the Impersonate preset, the wording of the default Options preset (5 aims for 3 Options, and "next story beat" against the closing line), the Quantifier model choice for this World. These belong to the second effort.
- An automated, repeated comparison with ST and ME (owner, charting).
- The design of long-term memory and long-term state: the writers, their schemas, caps, cost, trigger (compaction or each scene) and block position. A new effort, because it is a feature the size of Autoplay and this map is about changeable call parts. See [Decide whether this map designs memory and state, or only keeps room for them](issues/16-memory-and-state-scope.md) and the [seed](../long-term-memory-and-state/idea.md).
