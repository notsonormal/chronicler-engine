# Map: Layout trials

Labels: wayfinder:map

## Destination

Each layout candidate is tried in a trial and kept or dropped, or it is set aside with its reason. The engine has each kept candidate. The criteria that the owner used to read the trials are written down. The map has decided whether an LLM judge is necessary.

## Notes

- **Origin (owner, 2026-11-01).** This map is split from [Prompt flexibility](../prompt-flexibility/map.md). That map built the trial tool and fixed the measured faults in the prompts, but it ran no layout trial. Its layout decision is in [Decide which parts of a Narrator-role call an author can change](../prompt-flexibility/issues/06-the-layout-model.md): the layout stays an engine rule until a trial shows that a change helps the output or the cache. That ticket lists the candidates, and this map tries them.
- **What the trials are for (owner, charting).** The trials decide the candidates, and the method grows from use. First the cache candidates, which a number decides. Then the output candidates: the owner reads the packs, and the map writes down what the owner looked for. Those notes become the criteria. The notes also decide whether an LLM judge is necessary. Criteria or a judge written before anyone compares two real packs are a guess.
- **The target part (owner, charting).** Each candidate names the part of the story that it targets: the Narration, or the Inputs that Impersonate writes for the Persona. The reading looks at that part, so that a change in the other part does not hide the effect.
- **Cache candidates (owner, charting).** The cached share alone decides: keep the candidate when the share goes up. One trial for each side. Owner: "better or worse is hard to determine anyway"; make something sensible for the cache, and decide the rest later.
- **A cache candidate is measured before its trial (owner, plan review, 2026-11-01).** [`prefix_measure.py`](assets/prefix_measure.py) first measures the candidate on the prompts of the baseline pack. This costs no tokens and has no noise from a second story. Only a candidate with a clear gain gets a trial, and that trial confirms the provider's number.
- **One cache candidate (owner, plan review, 2026-11-01).** The presence marks, `<GameState>` and `<CharactersPresent>` are one candidate: [Try the changing blocks after the history](issues/03-changing-blocks-after-history.md). Each part alone gains about 1 to 4 points, and together they gain about 28 points ([measure](assets/cache-prefix-measure.md)), because a move of a Character or a Room changes `<CharactersPresent>` too.
- **One test setup (owner, charting).** Every comparison uses `scripts/trial_setups/redmist_julian.json`: the World `redmist_estate`, the Persona `julian`, novel mode, third person and past tense, the default presets, and OpenCode Go `deepseek-v4.1-flash` for every call. A result holds for this World, this mode and this model. [Decide how to read an output trial](issues/05-read-an-output-trial.md) can add a second model for the role candidates.
- **Decide, then build (owner, charting).** A trial ticket only decides. A kept candidate gets a new task ticket that makes the change test first and ends with `/simple-after-plan`: the comment pass, the doc review, `/code-review`, the full `python build.py`, and the retro. Each such ticket changes the docs that its change makes wrong (`docs/AGENTS.md`, "Direction of edits").
- **One branch, and worktrees (owner, charting).** The whole map works on one branch, `layout-trials`, made from `main` after `prompt-flexibility` merges. A trial runs its candidate in a linked worktree made from `layout-trials`, with a detached HEAD and its own probe server, so two trials can run in parallel. Nobody merges trial code: the worktree goes away after its trial. A kept-candidate ticket makes the change on `layout-trials`.
- **How a trial runs (known).** `python scripts/trial.py run <setup.json>` plays the setup against a probe server (`/chronicler-ui-investigator`), and `python scripts/trial.py compare <pack> <pack>` puts packs side by side. The setup file sets the output folder (`out`), so each ticket runs a copy of the setup file under `tmp/<ticket>/`. The `connections` ids of the setup file must exist in the probe DB. A worktree's probe server starts with a copy of the main probe DB (`target/ui-investigator/debug/chronicler_3001.db`, copied with the SQLite backup call as in tickets 21 and 22 of Prompt flexibility), so that both sides use the same "Go check" Connection. A fresh DB seeds other Connection ids from `data/settings.json`. `trial.py run` takes `--base` and `--db` for a server that is not on port 3001. A 100-Cycle trial uses about 3 M tokens and about 20 minutes (the last trial of Prompt flexibility: 3,042,919 input tokens, 1241 s, 50 % cached).
- **Worktree limits (known).** The probe server reads `.env` from its working folder, and an agent may not read `.env` files. Start the built binary from a scratch folder under `tmp/` of the main checkout, so that the server loads the `.env` above it, as tickets 20 to 22 of Prompt flexibility did. Never read or print a key. The full gate runs `scripts/remove_worktrees.py`, which keeps a dirty worktree, a worktree younger than 24 hours, and a worktree with a live process inside it.
- **What already exists (plan review, 2026-11-01).** `scripts/trial.py` (`run`, `export`, `compare`, and the cached tokens of each call kind in `pack.md`) with its tests in `scripts/tests/test_trial.py`. [`prefix_measure.py`](assets/prefix_measure.py) measures the shared prefix of a pack, today and with a cache candidate applied, with no model call ([result on the last trial](assets/cache-prefix-measure.md)). `/chronicler-ui-investigator` starts a probe server. `scripts/target_seed.py` seeds the cold target dir of a new worktree. `scripts/remove_worktrees.py` removes a worktree only when it is safe to lose.
- **Failure modes (plan review, 2026-11-01).**
  - A trial stops early (a `content_filter` past the restart limit, or the token limit). Then two trials of a comparison have different lengths, and only the Cycles that both played compare.
  - The two sides use different Connection values, because a worktree started with a fresh DB. The comparison then measures the Connection, not the candidate. Copy the main probe DB.
  - A layout change hides a part that `scripts/trial.py` finds by its text: `<ConversationHistory>` in the user prompt (the history columns of the pack), or "player character" in the system prompt (the Impersonate label). The pack is then wrong with no error. After each candidate trial, check that the pack still shows the history and the call kinds.
  - The probe server of a worktree finds no `.env`, and every call fails. Start it from a scratch folder under `tmp/` of the main checkout.
  - Two trials in parallel use one OpenCode Go key. The rate limit of the key is unknown (guessed risk). If calls fail with a rate error, run the trials one after the other.
- **Names (owner, charting).** "Trial", "test setup", "reading pack" and "candidate" are working names. No `CONTEXT.md` changes.
- **Skills.** `/research` for the research ticket, `/grilling` for the grilling ticket, `/chronicler-ui-investigator` for the probe server, and `/simple-after-plan` for a kept candidate. Read `docs/diataxis/reference/narrative/prompt_system.md` and `docs/diataxis/explanation/prompt_system_design.md` first.
- **Standing rules (from Prompt flexibility).** Write plans directly in the repo, not through Plannotator. Any new API takes a `GameId` and adds no read of `ActiveGame`. A migration takes the next free step, adds a column with `ALTER TABLE … ADD COLUMN` guarded by `column_exists`, never edits an old `CREATE TABLE`, raises `LATEST_VERSION`, and gets its test in `plumbing_tests.rs`.
- **Sources.** From Prompt flexibility: [Shape the test setup and the trial](../prompt-flexibility/issues/08-test-setup-and-trial.md), [Write the build plan for the engine changes](../prompt-flexibility/issues/09-build-plan.md) (how a trial runs a layout change), [Find how prompt caching works for our providers and our layout](../prompt-flexibility/issues/12-prompt-caching.md), [Cut the history in blocks](../prompt-flexibility/issues/20-cut-the-history-in-blocks.md) (the last trial), and [the trial prototype](../prompt-flexibility/assets/trial-prototype.md).

## Decisions so far

<!-- the index — one line per closed ticket: enough to judge relevance, then zoom the link for the detail the ticket holds -->

- [Run the baseline trial](issues/01-baseline-trial.md) — ran 100 Cycles on `1a0c9162` with no failed call, 47.6 % cached (Quantifier 3.8 %). The pack is the reference in `tmp/lt01/redmist_julian/trial-1`. The Impersonate output is about 31 % longer than in pf20.
- [Find why the Quantifier calls read so little from the cache](issues/02-quantifier-cache.md) — the stable front is already 6 to 7 cache units of 128 tokens, and an identical front hits on only 15 % of calls. No layout change helps ([asset](assets/quantifier-cache.md)). The research did not test the shared OpenCode session value, so [Try a separate OpenCode session for each call kind](issues/10-separate-session-per-call-kind.md) tests it.
- [Try the changing blocks after the history](issues/03-changing-blocks-after-history.md) — keep. The cached share went from 47.6 % to 68.9 % (Narrator-role calls 55.2 % to 78.8 %), and `prefix_measure.py` predicted the gain well. [Move the changing blocks after the history](issues/09-move-changing-blocks-after-history.md) builds it.

## Not yet specified

- **The LLM judge.** The owner's notes from the output readings decide whether a judge is necessary, and what it checks. Every tool that [Find the tools that evaluate characters and prompts](../prompt-flexibility/issues/05-evaluation-tools.md) found judges one reply, so a check across a whole story (repetition, voice drift over the Cycles) may be new work.
- **The length of the Impersonate output.** [Add the connection slots and remove the global response length](../prompt-flexibility/issues/21-connection-slots-and-response-length.md) removed the "Response Length" text from the Impersonate prompt on purpose. In [Run the baseline trial](issues/01-baseline-trial.md), the median Impersonate output went from 650 to 853 tokens. But [Try the changing blocks after the history](issues/03-changing-blocks-after-history.md) also had no length text, and its median Input was 131 words (baseline 160, pf20 126). So the length change is probably story noise (inferred). Does the default Impersonate preset need its own length text? This is an output question about the Inputs, so it waits for [Decide how to read an output trial](issues/05-read-an-output-trial.md).
- **A new baseline after a kept candidate lands.** When a kept candidate is in the engine, does the next comparison need a new baseline trial, or does the first baseline stay the reference?

## Out of scope

- **The author controls:** author-editable instruction sentences (the Event Narration frame, the Guide sentence, the history-cut marker) and an author block order. Both are candidates of [Decide which parts of a Narrator-role call an author can change](../prompt-flexibility/issues/06-the-layout-model.md). They give the author control and do not change the default output, so a trial cannot show their value. Decide them when an author needs them, in the authoring effort (owner, charting).
- **Other test setups:** other Worlds, other Personas and interactive fiction mode. They need authoring work first (owner, charting).
- The authoring of the World, the cards and the presets: a separate effort that uses what this map learns.
- The design of long-term memory and long-term state: a separate effort ([seed](../long-term-memory-and-state/idea.md)).
