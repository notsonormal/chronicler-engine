# Review 15: design and build decisions against standard practice

Reviewer: rev-kimi. Scope: the turn-state-model design (target-design.md v2, sketch 25, sketch 24) and platform-choice decisions (tickets 05, 08, 09, 11, 12, 13). Read-only; no code run.

## 1. Verdict

The design is mostly sensible and materially simpler than today's code: it deletes the Snapshot, the Retry anchor, the arrival opening, and the `Storage::game_id` global. Those are good standard moves. The worry the owner voiced is real, but it shows up less in any single choice than in the *proportion of mechanism* the design now needs: 18 guardrail rules, four custom syn walkers, one large core build step, and the deletion of about 7,400 unit-test lines. The design is not obviously broken, but it has accumulated enforcement and migration machinery that is unusual for a single-user, single-process SQLite web app. Before the build plan is written I would shrink the guardrail surface, preserve more unit tests, and split the core step.

## 3. Parts that are standard or sensibly simpler

- **Derived current state from the last Swipe's state** (D-01/D-02) is a standard denormalization/read-model pattern; it removes the Snapshot restore step and the Retry anchor.
- **Per-Swipe state copies** trade storage size for immutability and replay-free correctness; this matches Marinara's design and is a defensible standard trade-off.
- **Transaction-scoped save units** (D-04, ticket 11) are standard unit-of-work practice.
- **`SavedText` token** (ticket 05 G2) is a standard Rust idiom: use move semantics to enforce "exactly one state update per saved text."
- **Agents as a hook/plugin registry** (sketch 24) is a standard extension pattern; four small traits with typed outputs is cleaner than today's `AgentResult` merge loop.
- **Narrow reads for views** (sketch 25 §3.4) replace whole-`GameState` loads and are standard CQRS/read-model thinking.
- **No LLM opening** (D-25) removes a special-case code path; the opening becomes a normal Message.

## 4. Top three changes before the build plan is written

1. **Shrink the guardrail surface.** Eighteen rules, four custom AST walkers, and a generator change are too much mechanism for a single-process app. Keep the compiler-level and arch-lint rules, and replace the call-site/call-count/type-check walkers with simpler code structure: for example, make `generate` a real state machine or unit-of-work type so the "one step", "pass ids", and "one hold" invariants fall out of the data structure instead of being linted after the fact. If walkers remain, require each rule to prove it catches a defect the compiler cannot.

2. **Preserve unit tests for pure domain code.** The "unit test only inside a seam contract" rule should not apply to `domain/model/` (`Tail`, `SwipeState`, `GenerationOrder`, `apply_game_rules`). These modules have no I/O and many branches; fast unit tests are exactly the right tool. Deleting them all in favour of HTTP scenarios will make regressions harder and slower to find. The build plan should list which pure modules keep unit tests and how many.

3. **Break the core step into two or three mergeable cuts.** A single branch that changes the records, the writer, the pipeline, the views, create/reset, and deletes the old code is a big-bang rewrite. Plan at least one intermediate state where the new `SwipeState`-based records coexist with the old pipeline behind a router or flag, so the repository can stay green and reviewable. The temporary adapter is cheaper than the risk of a long-lived core branch.
