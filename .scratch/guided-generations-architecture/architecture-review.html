1. The replay blob has no owning module

Strong in-process

Files

src/domain/model/state/game_state.rs (push_message) · src/application/pipeline/action_pipeline/action.rs

Before — blob lifecycle scattered

  A[action.rs
builds blob] --> B[narrative_state
pending_replay]
  B --> C[game_state
push_message copies onto swipe]
  C --> D[pipeline_run
reads blob back via resolve_*]
  D --> E[retry.rs

  A -.leak.-> E
  classDef leak stroke:#dc2626,stroke-width:2px,color:#7f1d1d;
  class A,B,C,D,E leak

After — one ReplayBlob module

ReplaySteering module

stage() · attach_to_swipe() · resolve_for_turn() · resolve_for_retry()

owns the invariant: steering is transient, rides on the swipe, re-applied on retry

action.rs, game_state, pipeline_run, retry all call the same 4-method interface

Problem

The invariant "steering is transient and rides on the swipe's replay blob" is enforced by no single module. Six files jointly maintain it; understanding the lifecycle means bouncing between all six. Lost locality.

Solution

A ReplaySteering module owns stage → attach → resolve-for-turn → resolve-for-retry. The blob value type stays in message.rs; the lifecycle moves behind one interface.

Wins

  • locality: blob invariants concentrate in one module
  • interface shrinks: 4 methods replace 6 scattered reads/writes
  • leverage: retry + pipeline + game_state all cross one seam
  • tests hit one interface, not pub(crate) internals

2. Retry is a shallow mixer duplicating the narrate turn

Strong in-process

Files

src/application/pipeline/action_pipeline/retry.rs (+345)
src/application/pipeline/pipeline_run.rs (phase_narrate, +177)
src/application/message_service.rs (find_retry_anchor_msg)

Before — two shallow modules, duplicated choreography

retry.rs interface (wide)

retry_reimpersonate · retry_user_regen · retry_event · retry_main · resolve_target · reconstruct_state

implementation: load bundle → room → preset → PromptContext → narrator → save (copied)

≈ duplicate of ↓

phase_narrate interface (wide)

load bundle → room → preset → PromptContext → narrator → save

After — one deep NarrationTurn module

NarrationTurn module

run(state, steering) → Outcome

owns: bundle load, room resolve, preset select, prompt build, narrator call, save

phase_narrate calls it retry_* calls it

retry becomes mode-routing only; choreography lives once

Problem

retry_reimpersonate and retry_user_regen duplicate phase_narrate's choreography (bundle → room → preset → context → narrator → save). No deep module owns "run one narration turn from a prepared GameState." Retry tests reach into pub(crate) helpers because the public flow can't be driven with blobs.

Solution

Extract a NarrationTurn module with one interface: run(state, steering) → Outcome. phase_narrate and all retry modes call it; retry keeps only mode-routing (ReNarrate / ReImpersonate / UserRegen) and anchor selection.

Wins

  • locality: one narration-turn implementation, not three
  • leverage: phase_narrate + 3 retry modes share one interface
  • interface shrinks: retry drops ~150 lines of duplicated choreography
  • tests drive the public seam; pub(crate) helpers retire
  • retry-mode policy (anchor + mode) localises with message_service split resolved
Supporting friction: retry-mode policy is itself split — message_service.rs::find_retry_anchor_msg picks the anchor, retry.rs::resolve_retry_target classifies the mode. Deepening retry concentrates both.

After — one dispatcher behind the Action seam

flowchart TD
  H[HTTP handler] --> A[Action enum
parser already exists]
  A --> D[process_action Action]
  D --> T{match steering}
  T -->|Free| F[free-turn path]
  T -->|Guide| S[Steering payload]
  T -->|Narrator| S
  T -->|Impersonate| S
  S --> R[stage replay blob]
  classDef deep fill:#1e293b,color:#f8fafc,stroke:#0f172a;

Problem

HTTP already maps slash commands to Action variants cleanly. The pipeline then re-derives the same mapping through seven entry methods. impersonate also reads settings.active_impersonate_prompt_preset_id directly, coupling the entry path to preset management. Shallow routing: interface nearly as wide as the implementation.

Solution

Collapse the seven methods into one process_action(Action) dispatcher. Steering payload (guide / impersonate preset id / direction) rides on the Action enum, which already exists. Preset resolution moves behind the dispatcher, not into the entry method.

Wins

  • interface shrinks: 7 methods → 1, parametrised by Action
  • locality: steering routing concentrates at the Action seam
  • leverage: HTTP and tests cross the same dispatcher
  • preset lookup stops leaking into the entry path

4. Prompt-construction seam split between assembler and pipeline_run

Worth exploring in-process

Files

src/application/prompting/assembler.rs (PromptContext, render_persona_layer, render_guide_layer)
src/application/pipeline/pipeline_run.rs (phase_narrate preset selection)

Before — impersonate knowledge in two places

pipeline_run: selects impersonate preset (swaps system preset)
assembler: drops player-character layer on impersonate
PromptContext::with_impersonate: clears guide (mutual-exclusion rule)
no single module knows "what impersonate means for the prompt"

After — impersonate policy behind one interface

SteeringPromptPolicy module

resolve(steering) → PresetChoice + LayerSet

owns: preset swap, layer drop, guide/impersonate mutual exclusion

pipeline_run calls it assembler calls it

Problem

"What impersonate does to the prompt" is split: preset swap in pipeline_run, layer drop in assembler, mutual-exclusion in PromptContext. Neither module is deep on its own; they form a tightly coupled seam. A change to impersonate's prompt shape touches both.

Solution

A SteeringPromptPolicy module returns the preset choice and the layer set for a given steering. pipeline_run and assembler consume its output; neither owns impersonate specifics.

Wins

  • locality: impersonate prompt shape lives in one module
  • interface shrinks: PromptContext drops guide/impersonate fields
  • mutual-exclusion rule stops hiding in a builder method
  • tests: one interface for "what does steering X do to the prompt"

5. Narrative-voice setting leaks across two injection points

Worth exploring in-process

Files

src/application/prompting/assembler.rs (assemble → set_narrative_voice)
src/application/arrival_service.rs (ArrivalTaskContext::run → set_narrative_voice)
src/domain/model/template.rs (TemplateVars::set_narrative_voice)

Before — two callers must remember

flowchart LR
  S[AppSettings
narrative_voice] --> A1[assembler.assemble
set_narrative_voice]
  S --> A2[arrival_service.run
set_narrative_voice]
  A1 -.leak.-> T[TemplateVars]
  A2 -.leak.-> T
  T --> D[defaults to 3rd/past
silent wrong voice]
  classDef leak stroke:#dc2626,stroke-width:2px;
  class A1,A2 leak

After — assembler owns voice application

flowchart LR
  S[AppSettings] --> A[assembler.assemble]
  A --> T[TemplateVars
voice applied once]
  A2[arrival_service] --> A
  classDef deep fill:#1e293b,color:#f8fafc;
  class A deep

Problem

set_narrative_voice is called in both assembler.assemble and arrival_service. Any future caller that builds a PromptContext must remember to apply it; forgetting it silently produces third-person-past output. A leaking seam.

Solution

The assembler already holds AppSettings and applies voice in assemble. Route arrival_service through the assembler (or a shared TemplateVars builder) so voice is applied at the single owner of prompt construction.

Wins

  • locality: voice policy lives in the prompt-construction module
  • one call site, not two — silent-wrong-voice failure mode gone
  • leverage: any new PromptContext caller gets voice for free

Top recommendation

Start with Candidate 2 — extract the NarrationTurn module

It unblocks the others. A deep NarrationTurn module that owns "run one narration turn from a prepared GameState" gives Candidate 1 (ReplaySteering) a single consumer to call against, retires the pub(crate) test helpers, and removes ~150 lines of duplicated choreography between retry.rs and phase_narrate. Candidates 3 and 4 then layer on top of a stable narration-turn seam. Candidate 5 is independent and small — a safe parallel win.
