# Research 07: the readers of the Message history and its Snapshot pointers

Ticket: [Research: list the readers of the Message history and its Snapshot pointers](../issues/07-research-message-history-readers.md).

Labels: **known** = read in the code at the time of writing. **inferred** = follows from the code but was not run. **tested** = an existing test pins it.

Method: `rg` over `src/` for `snapshot_id`, `load_snapshot_by_id`, `load_latest_snapshot`, `messages.last()`, `history()`, `MessageType::System`, `location_header`, `event_header`, `guide_text`, `MessageEntry`. `*_tests.rs`, `src/test_support/` and `tests/` are excluded from the reader tables; a test is named only where it is the evidence. S-labels (`Sc`, `S0`, `S1`, `S1'`, `S2b`, `S3`, `S5`, `S5'`, `S6`, `Sf`, `Sr`, `So0`, `Si`, `Sa`, `Ss`) are the ones defined in [research 04](research-04-generation-snapshots.md); that asset's sequences and pointer rules are assumed, not repeated.

## 0. Two facts that frame every table

- **known.** The only three code sites that read a Message or Swipe `snapshot_id` and load it are `MessageService::switch_swipe`, `ActionPipeline::retry_last_response` and `ActionPipeline::check_retry_anchor`. Everything else that needs a state calls `Storage::load_latest_snapshot` through `MessageService::load_expecting_valid_state` / `load_or_fresh`. Confirmed by `rg 'load_snapshot_by_id' src/`: three call sites — `MessageService::switch_swipe`, `ActionPipeline::retry_last_response` and `ActionPipeline::check_retry_anchor` — plus the definition in `adapters/driven/storage/snapshots.rs`.
- **known.** No file under `src/adapters/driving/http/` mentions `snapshot` at all. There is no render, fragment, view-query or debug path that loads a Snapshot by a Message or Swipe pointer; every one of them goes through `load_or_fresh` and therefore shows the **latest** Snapshot, whatever pointers the Messages carry. The `Ss` copy that `switch_swipe` writes is what makes the latest Snapshot the switched-to state.

## 3. Prompt readers

No prompt builder reads anything but `text` and `message_type`.

## 5. The two inherited claims

**Claim A — ticket 02's list of the five `System` sources is complete. Confirmed.**
`rg 'MessageType::System' src/` finds exactly five construction sites, all of them `GameState::add_message(text, MessageType::System)`:

| # | Source symbol | Text | Matches ticket 02 |
|---|---|---|---|
| 1 | `PipelineRun::phase_post_generation` | `[System] NPC detection uncertain — using room defaults` | yes (ticket 02 calls the file `pipeline_run.rs`; the function is `phase_post_generation`) |
| 2 | `ActionPipeline::finalize_options_failure`, called from `execute_options_refresh` | `[System] Options generation failed: {e}` — the same text for the bundle-load error and the agent error | yes — ticket 02's `persist_options_failure` is this function under a different name |
| 3 | `ActionPipeline::rewrite_options_after_turn` | `[System] Options agent is not available` | yes |
| 4 | `ActionPipeline::rewrite_options_after_turn` | `[System] Options generation failed: {e}` | yes |
| 5 | `GameState::attempt_movement` | `[System] Entered unknown location: {id}` | yes |

No sixth source exists in `src/`. `MessageType::System` is otherwise only **read**: the two agent prompts, `LayerRenderer::render_history_layer`, `MessageEntryView::from`, `Message::is_input_or_narration`, and the storage mapper (rows written by an older build still load).

**Claim A′ — ticket 02's list of the leaks is complete. Confirmed, and one is understated.**
- Narrator: `LayerRenderer::render_history_layer` renders `System: {text}` — confirmed.
- Quantifier: `QuantifierPromptBuilder::build_user_prompt` — confirmed.
- Options: `OptionsPromptBuilder::build_user_prompt` — confirmed.
- `show_retrigger`: `NarrativeLogTemplate::new` — confirmed.
- Swipe controls: the template's `loop.last && (narration || input)` — confirmed and **tested**.
- `retrigger.rs` and `MessageService::switch_swipe` use the last Message — confirmed; `switch_swipe` is the harder failure (it returns a validation error, so the control is dead, not merely hidden).
- Retry anchor and target skip them via `Message::is_input_or_narration` — confirmed.
- **Understated, additions.** (a) The **Trigger continuation prompt** (`PipelineRun::build_trigger_request`) renders them too — ticket 02 lists only three prompts. (b) `ActionPipeline::retry`'s pre-claim guard `MessageHistory::last_turn_is_retryable` **does not** skip them; it only searches for the last Input and the last input-or-narration. (c) `MessageService::delete_last` deletes a trailing `System` (the Delete button is on it) instead of the Narration, and `edit_history` edits it. (d) `GameState::push_message` lets a `System` Message consume `pending_location` and `pending_event`, so a notice can carry a location or event header (see Open points). (e) Each one is saved with a Snapshot through `save_message_and_snapshot`, and the `System` Message takes the pointer — the Snapshot-chain leak ticket 02 names.

**Claim B — "no prompt reads `location_header`". Confirmed.**
`rg 'location_header' src/` returns the model (`Swipe`, `Message::location_header`, `Message::set_location_header`), `MessageEntry` (the field plus its `From`), `MessageEntryView`, `GameViewQuery`-adjacent plumbing, the storage layer (schema, `update_swipe_location_header`, row mapper) and the `NarrativeLogTemplate` source. The only two writers are `GameState::log_movement_completion` and `MessageService::save_arriving_location`; the only reader outside the domain and storage layers is the story-log template (plus `dashboard-story-log.js` indirectly through the rendered HTML). No file under `src/application/prompting/` or `src/application/agents/` mentions it.

**Claim B′ — the same holds for `event_header` and for the Swipe metadata.** `event_header` is read only by the retry anchor logic, `GameState::push_message`, `retrigger.rs`, `MessageHistory::is_last_ai_response_event_continuation`, `MessageEntry::from`, `MessageEntryView::from` and the template. `guide_text` / `impersonate_direction` do reach the LLM, but through `ActionPipeline::run_from_input` reading `narrative.retry_target` on a redo — never through `MessageEntry`.

## 6. Open points for later tickets

1. **`check_retry_anchor` validates a pointer the redo does not restore (event branch).** *Known from the code; the consequence is inferred.* `check_retry_anchor` loads the **anchor's** `snapshot_id()`, but `retry_last_response` restores `old_target.snapshot_id()` (the event Message's own pointer) when `target.is_event`. For every other mode the two coincide. So the guard can pass and the redo then fail with `Retry failed: no snapshot found for id …`. No ticket on this map covers it; ticket 06 (retry tails) or 01 (the pointer model) should.
2. **The story log caps at the first 50 entries, not the last 50.** *Known from the code.* `AppState::render_story_log` does `entries.into_iter().take(MAX_LOG_DISPLAY)` on a chronological list, while `NarrativeLogTemplate` attaches Delete, Retrigger and the Swipe controls to `loop.last`. Once a Game has more than 50 Messages, those controls belong to Message 50 and the newest Messages render without any control. `get_debug_state` has the same shape but takes from the end (`rev().take(5).rev()`), which makes the difference look like an oversight. No ticket covers it.
3. **A `System` or `Input` Message can consume `pending_location` / `pending_event`.** *Known from the code.* `GameState::push_message` calls `pending_location.take()` and `pending_event.take()` before the type check, and `Message::new` stores them for every `MessageType`. The one path where this can be reached today is the unknown-room `System` Message in `GameState::attempt_movement`, which runs inside `handle_movement` — after the Narration, so normally nothing is pending. Ticket 03 and ticket 08 should confirm whether any reachable ordering lets a notice take a header; it is the same "display data inside the Message history" problem ticket 03 weighs.
4. **Dead last-Message helpers.** *Known from the code.* `MessageHistory::is_last`, `last_ai_response_index`, `last_input_index` and `is_last_ai_response_event_continuation` have no production caller; `switch_swipe` re-implements `is_last` locally on a freshly loaded `Vec<Message>`. If ticket 01 rewrites the "last Message" rules, these are the symbols to delete rather than extend. (`last_mut` is live, but only for the two initial-state writers.)
5. **`delete_last` leaves the deleted Message's Snapshot rows behind.** *Known from the code; the storage consequence is inferred.* `MessageService::delete_last` hard-deletes the Message (`Storage::delete_message`), the Swipes cascade, and the Snapshot rows that the Swipes pointed at stay in the `snapshots` table (`snapshot_id` is deliberately not a foreign key). Nothing reads them once the Message is gone, and `load_latest_snapshot` orders by `created_at DESC`, so a later Snapshot still wins. Worth one line in ticket 05's writer model, not a defect by itself.
6. **`switch_swipe` copies the Snapshot instead of pointing at it.** *Known from the code.* It writes a **new** Snapshot row (`Ss`) with `Idle`, a default phase and no options, and leaves the Message's `Swipe::snapshot_id` untouched. Ticket 01's model must say whether a swipe switch is a state write of its own (it is a writer with no generation slot) or a pointer move; ticket 13 and ticket 14 (the reference engines' swipe binding) are the place to compare.
