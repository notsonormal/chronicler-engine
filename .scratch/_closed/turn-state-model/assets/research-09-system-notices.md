# Research 09: routing each `System` notice to an existing channel

Ticket: [Research: route each System notice to an existing channel](../issues/09-research-system-notice-channels.md).
Feeds: [Replace `System` Messages with an error channel outside the Message history](../issues/02-replace-system-messages.md).

Labels: **known** = read in the code at the time of writing. **inferred** = follows from the code but was not run. **tested** = an existing test pins it.
Method: `rg 'MessageType::System'`, `rg '\[System\]'` and `rg 'message_type'` over `src/`, `tests/` and `docs/specs/`; every source read in full at its construction site. No build was run.

## 0. Framing facts

- **known.** `MessageType` has three unit variants (`Narration`, `System`, `Input`) in `domain/model/state/message_types.rs`; it serializes as its variant name (the `messages.message_type` column holds `'"System"'`).
- **known.** Exactly **five** construction sites exist in `src/`, all `GameState::add_message(text, MessageType::System)` → `GameState::push_message`. Ticket 02's list is complete; there is no sixth. No `/action` handler, bootstrap seed, arrival path or agent builds one directly.
- **known.** Read sites in non-test code, none of which constructs the type: `LayerRenderer::render_history_layer` (`prompting/assembler.rs`), `QuantifierPromptBuilder::build_user_prompt`, `OptionsPromptBuilder::build_user_prompt`, `MessageEntryView::from` (`http/view_models.rs`, `log_type = "system"`), `Message::is_input_or_narration`, `GameState::push_message`'s swipe guard, the message mapper (`serde_json::from_str`), and the retry target/anchor predicates (`retry.rs`, `message_history.rs`). Ticket 07 covers these.
- **known.** Every site adds the notice as a **new Message with one Swipe** (`push_message`'s guard admits only `Narration`/`Input` to the swipe-append path), and it still `take()`s `pending_location` / `pending_event` first.

`Kind`: **failure** = an LLM/agent call failed; **fallback** = the turn continued on defaults; **gap** = world data did not answer.

Per-source coverage notes (all **known**):

- **#1 splits in two.** A **failed Quantifier LLM call** (`quantify_room_with_llm_call` exhausts `max_attempts`, returns empty + `Low`) makes the branch fire *and* writes an `llm_messages` row with `error_message` via `LlmCallRecorder::failed_message`, so `role_failure_sentence(Role::Quantifier)` — "Quantifier failed — using fallback NPC IDs" — already says it, engine-wide. A **low/medium-confidence success with no parsed NPCs** fires the same branch with **no** failed row: nothing but the notice reports it. The branch also restores `state.scene.npcs_in_area` as the defaults — the same thing `static_npc_result` already did, so the notice is purely informational.
- **#1 fires only when the room's in-area list is empty** (**inferred**): `process_quantifier_result` routes `Low` confidence to `static_npc_result`, which copies `scene.npcs_in_area` into `npc_ids`. A non-empty room list therefore makes `npc_ids.is_empty()` false and suppresses the notice — a quantifier failure in an occupied room is silent.
- **#2/#4's error text is raw engine text** (`{e}` from `EngineError`), exactly what `GenerationFailure::raw` is for and what `generation_failure_summary` + `raw_error_detail` exist to clamp.
- **No spec asserts #1 or #5** (`rg -i 'unknown location|NPC detection' docs/specs/` → nothing). Both are unit-test-only.
- **the ticket-10 pattern covers none of the five as-is.** Ticket 10 removed the notice and relied on (a) `GenerationStatus::Error` with `with_context("Trigger narration failed")` and (b) the banner reading the recorder's failed Trigger row. Only #2's and #4's transport flavour have (b); none has (a), because a failed *optional* step finishes the turn as non-error on purpose ("finish the run as a normal (non-error) turn" — `finalize_options_failure`).

## 3. Stored data

- **known — how a notice is saved.** `MessageService::save_message_and_snapshot` calls `save_arriving_location`, writes one Snapshot (`write_snapshot`), then walks `state.narrative.history` and, for every `Message::is_unpersisted()`, sets `Message::set_snapshot_id` and its first `Swipe::snapshot_id` to that Snapshot id and inserts the rows. A `System` Message is an ordinary Message here: it becomes the last row, owns a Swipe that points at the turn's Snapshot, and takes part in the pointer chain Retry/Swipe restore. Callers that can carry a notice: `PipelineRun::persist_snapshot_or_err` and the best-effort saves in `phase_post_generation`, `ActionPipeline::finalize_options_failure`, `rewrite_options_after_turn` (×2), `core.rs` post-engine commit, `arrival_service.rs`, `generation/gate.rs`.
- **known — what breaks if the variant goes.** `mappers/message.rs` does `serde_json::from_str(&db.message_type_json)?` **inside the row loop** of `Storage::load_message_rows`, so one unparsable row fails the whole `load_messages_with_swipes`. `MessageService::load_messages_into_state` swallows that error (`if let Ok(msgs) = …`), leaving the history as whatever `GameState::from_snapshot` produced, and `load_or_fresh` then logs "Failed to load game state … building fresh initial state" and can rebuild from the scenario. So **a render rule alone is not enough** — an old Game with a stored `System` Message would silently lose its entire history (**inferred** from that code path; not run).
- **known — the migration pattern.** `run_migrations` in `adapters/driven/storage/utils/plumbing.rs` is a sequence of `if version < N { … pragma_update("user_version", N) }` blocks inside one transaction, with `column_exists` guards and `UPDATE …` backfills for data rewrites (v22 moved `message_swipes.replay` JSON into two columns and dropped it; v25/v23/v26 are game-row backfills). The test pattern is `utils/plumbing_tests.rs`: build the old shape with raw SQL, `run_migrations`, assert — `test_v22_backfills_swipe_inputs_from_replay_blob_and_drops_column` inserts `'"Narration"'` into `messages.message_type` exactly as a v27 backfill of `'"System"'` would. A one-line `UPDATE messages SET message_type = '"<new value>"' WHERE message_type = '"System"'` in a `if version < 27` block is the whole migration (**inferred**: shape only, no decision here about the target value).
- **known — code paths that need a new rule if the type goes away.** 4 exhaustive `match entry.message_type` sites (`prompting/assembler.rs`, `agents/options/prompt.rs`, `agents/quantifier/prompt.rs`, `http/view_models.rs`); the type-dependent predicates `Message::is_input_or_narration`, `GameState::push_message`, `MessageHistory::last_*`, `ActionPipeline::resolve_retry_target`/`find_retry_anchor_msg`, `retrigger.rs`'s last-Message guard, `MessageService::switch_swipe`'s `is_last` check; 2 CSS rules (`.log-entry.system`, `.log-entry.system .text`); and the storage mapper. If legacy rows are migrated away, none of these needs a special case — only the deleted variant does.
- **known — `CONTEXT.md`.** Its **Message** entry reads "player input, narration output, event continuation, or system log"; `docs/diataxis/reference/storage.md` describes a `messages` row as "(player input, narration, system message)". Both would change with the decision.

## 5. Open points for ticket 02's grilling

1. **Does the player need to see each notice at all?** #1 is informational (its defaults are the same `static_npc_result` fallback), #5 is a world-data gap, #3/#4 leave the dock empty with no other signal. Only #2/#4 (raw engine text) is clearly an error.
2. **Which channel, per source** — the status line is the only channel that is per-Game, persisted, and free of the 50-row retention the banner depends on, but it is `GenerationStatus::Error`-shaped: does a *non-fatal* notice need a new status value, a new `GenerationFailureKind`, or a separate one-line notice slot beside `input_buffer.status`?
3. **Banner wording.** `role_failure_effect(Role::Quantifier)` already says "using fallback NPC IDs" and `Role::Options` "showing no options"; if those sources move off the banner, the effect strings need review — and the banner still cannot carry a source with no LLM call (#3) or with a successful row (zero-parse).
4. **Migration or render rule** — the mapper's hard failure says migration (or a tolerant mapper); the target value for legacy `'"System"'` rows and whether the notice text is kept is a decision, plus a `plumbing_tests.rs` case.
5. **`CONTEXT.md` / `storage.md`** wording for the Message entry if the type goes; and who owns the notice text (engine prose vs raw `EngineError::to_string()`).
6. **Ticket 02 understates two things**: (a) the trigger-continuation prompt (`PipelineRun::build_trigger_request`) also renders `System:` lines (already recorded by ticket 07); (b) ticket 10's answer's claim that the NPC-fallback notice "is the only player-visible record of a silent NPC-detection degradation (the status line and the banner report failures only, not this fallback)" holds only for the low-confidence flavour — the failed-call flavour is already reported by the banner.
