## 0. What the header is (known)

- The room name is one nullable column: `message_swipes.location_header`. Its domain carrier is `Swipe.location_header`, reached only through the active Swipe (`Message::location_header()`, `Message::set_location_header()`).
- It is **display-only**: no prompt renders it (see the read table). `docs/diataxis/reference/game_flow.md` §Movement Branch states the rule the code implements: "The room a movement lands in is the location header of the Swipe whose generation moved the player."
- Two other room facts exist and are *not* the header: `MovementState.current_room_id` (+ `dynamic_rooms`) in every Snapshot, and `NarrativeState.pending_location`, the staging slot that `push_message` drains into the next Message.
- The header is a **change marker, not a per-Message room stamp**: only the Swipe whose generation moved carries it. Scenario 1.14 (`docs/specs/actions.md`) pins that the Message after the movement has none.

Notes (known):

- **The write-back is a two-step: set in memory + queue a row update.** The row update happens at the *next* `save_message_and_snapshot`, which on the main path is the post-engine save in the same turn. A save that is `MessageService::save_state` (i.e. `PipelineRun::persist`: `phase_finalize`, `persist_generation_error`, `restore_click_time_state_after_failed_redo`) does **not** apply it. So a queued write survives only until the next pointer-capable save.
- `NarrativeState.arriving_location_write` is `#[serde(skip)]`, and `NarrativeState::from_snapshot` resets it to `None`. A process crash or an engine-commit failure between the queue and the post-engine save loses the header for that Swipe (inferred: the row keeps the header it was inserted with, which is `pending_location` = `None`).
- `log_movement_completion` returns early when the room resolves to nothing, leaving `pending_location` untouched. No reachable path was found for that (every `attempt_movement` result either resolves on the map or inserts a dynamic room) — inferred.
- **The pre-fix writer (HEAD, and the shape ticket 03 describes) is different**: `log_movement_completion` set `pending_location = Some(room.name)` and the *next* `push_message` drained it. That is the "one Message late" behaviour of finding S6. The uncommitted work tree replaces it. **Contradiction to flag for ticket 03**: it describes "the next Message took it" as the past, which is correct, but `docs/plans/subplan-c-mapless-enablement.md` still specifies the old shape (§5).

### 1b. The header's life in one turn, in order (known)

```text
run_from_input (spawned, slot held)
  S1 "pre-quantifier narration"   save_message_and_snapshot → insert_swipe(location_header = pending_location)
                                  pending_location is None on a normal turn; only a leftover from a
                                  persisted Snapshot (see §5) can give the Narration a header here
  Quantifier                      → movement.current_room_id = B (in memory)
  phase_engine_commit             → log_movement_completion
                                      set_location_header("Room B") on the arriving Message's active Swipe (memory)
                                      pending_location = None
                                      arriving_location_write = Some({message_id, swipe_index, "Room B"})
  S3 "post-engine snapshot"       save_message_and_snapshot
                                      save_arriving_location → UPDATE message_swipes.location_header
                                      arriving_location_write = None
                                      then write_snapshot(S3); S3 gets no pointer from any Swipe
  [Trigger branch: the event Narration is pushed with pending_location = None → no header, ever]
  S6 options rewrite              save_message_and_snapshot (an earlier queued write would be applied here)
  Sf  phase_finalize              MessageService::save_state — applies no header write
```

```text
main Retry (spawned, slot held)
  Sc of the click           try_claim
  anchor restore            the Input's Sc → room A; history cut after the Input; retry_target = the Narration
  S1' "pre-quantifier narration"  the redo Swipe is inserted onto retry_target with location_header = pending_location = None
  Quantifier → B; engine commit writes the header onto retry_target's **active (new) Swipe**
  S3' "post-engine snapshot"      applies the write (retry_target.id + active swipe index)
  retry_target → history
```

Consequence of the queue-and-apply split: between the engine commit and the next `save_message_and_snapshot` the header exists only in memory and in `ArrivingLocationWrite`; a `save_state` in between (`persist_generation_error`, `phase_finalize`) writes the Snapshot without the row update, and the write is then only re-applied if another `save_message_and_snapshot` follows in the same process (inferred; the row keeps `NULL`).

### 1c. Code in the same area that never touches the header (known)

- `MessageService::edit_history` (`POST /history/:id`) rewrites Swipe **text** only and saves a fresh Snapshot; the header is preserved.
- `MessageService::delete_last` (`POST /history/delete`) removes the last Message; no header write.
- `MessageService::switch_swipe` sets `active_swipe_index` and copies the Snapshot; it never reads or writes `location_header`.
- `PipelineRun::reconcile_post_trigger_npcs` (the post-event Quantifier) updates only `scene`/encounter counters — it cannot move the player, so it can neither set a header nor invalidate one.
- `NarrativeGeneration`, the Quantifier and the Options agents never write a header; `retry_user_regen` and `retry_event_continuation` re-run no engine commit, so they produce no header at all.
- `MessageService::save_state`, `GameCatalogue::persist_initial_state_with_swipes` (after the insert), `MessageService::build_fresh_initial_state` (after `push_message`) and the bootstrap seed helpers write Snapshots without touching the column.

The mismatch is exactly one class of Swipe: **the Swipe of the generation that moved the player** (Narration Swipe 0, or the redo Swipe of a main/guided/re-impersonate Retry). Every other Swipe either has no header or (scenario/arrival) has one that matches its own Snapshot.

Reachability (known): `MessageService::switch_swipe` refuses any Message that is not the last, so a switch to a moving Swipe is only possible while that Narration is the last Message **and** has more than one Swipe — i.e. after a main or guided Retry (9.8, 22.5), or via a direct `POST /message/:id/swipe/0`. In a plain one-generation turn the moving Narration has a single Swipe, so the UI offers Retry rather than a switch and only a direct call reaches the mismatch.

## 4. What a Snapshot holds about the room (scope 5)

- `GameStateSnapshot.movement` is `MovementState { current_room_id: String, dynamic_rooms: HashMap<String, Room> }` (known). There is **no** `current_room_name` field anywhere today — that is `docs/plans/subplan-c-mapless-enablement.md`'s proposal, not code.
- `GameStateSnapshot.narrative` (`NarrativeSnapshot`) carries `pending_location`. After the ticket-15 fix it is `None` on the saved states of a moving turn (`log_movement_completion` clears it); for a game created from a scenario whose text renders empty it can be `Some(room)`.
- Consequences: a room **identity** is derivable from one Snapshot (`current_room_id`, plus `dynamic_rooms[id].name` for a dynamic room); a room **name** for an authored room needs `MapDef::get_room_by_id(id)` from the world bundle. So the header *string* is reproducible from a Snapshot, given the map.
- **Two consecutive Snapshots can be compared for "the room changed"** by string-equality on `movement.current_room_id`. Two caveats: (i) a dynamic room's id is `dynamic_<unix-seconds>`, so re-entering the same unknown place counts as a change; (ii) the comparison tells you only *that* it changed, not which Message changed it.
- **Does the HTTP story-log path load Snapshots? No** (known). `GameViewQuery::get_story_log_entries` → `MessageService::load_or_fresh` → `load_expecting_valid_state` loads exactly one: `storage.load_latest_snapshot()`. The per-Swipe `snapshot_id`s *are* in memory (the Swipe rows are loaded), but `MessageEntry`/`MessageEntryView` drop them. So a render that needs two Snapshots must add a read path: handler → `storage.load_snapshot_by_id(swipe.snapshot_id)` (Storage already exposes it, used by `switch_swipe`) + `storage.world_bundle_for(game_id)` for the map (already used by `GameViewQuery::get_current_room_view`). `AppState` holds `message_service: Arc<MessageService>` and `game_view_query: GameViewQuery` but **no `storage`**; `GameViewQuery` is the only read-side type that owns `Arc<Storage>`, so the new read belongs there (known).
- **Which snapshots exist to compare?** For a moving generation the interesting pair is (pre-move, post-move) = `S1` and `S3`. **No Swipe points at `S3`**: `save_message_and_snapshot` sets a pointer only for unpersisted Messages and for the last Swipe of `retry_target` when its `snapshot_id` is `None`, and the post-engine save runs after both are set; `persist_snapshot_or_err` discards the id it gets back. So today the story log can compare the moved generation's `S1` with its neighbour's Snapshot — `S1` and the previous Input's `Sc` hold **the same room** (pre-turn), i.e. comparing them reports "no change" and reproduces the one-Message-late attribution, one Message further in. This is the core data gap of option B.

## 6. Old Games and the migration helpers (scope 6)

- **Only one row carries a header: `message_swipes.location_header`** (`TEXT`, nullable). `games`, `game_state_snapshots`, `messages` and every other table have no header column (known: the v9 `CREATE TABLE` block plus all later `ALTER`s in `run_migrations`).
- **`src/adapters/driven/storage/utils/plumbing.rs` does only one thing about it: the column is born in the `CREATE TABLE IF NOT EXISTS message_swipes` block (migration v9).** There is no `ALTER TABLE message_swipes ADD COLUMN location_header`, no `column_exists(conn, "message_swipes", "location_header")` guard, and **no backfill or normalisation of any value** — unlike `replay`, `impersonated`, `steering_instruction`, `guide_text` and `impersonate_direction`, all of which have `column_exists`-guarded `ALTER`s and (where needed) `UPDATE` backfills. `plumbing_tests.rs` has no test that mentions `location_header`.
- That is safe for the shapes that exist (known from git history): `message_swipes` was introduced **with** `location_header` (`16bef514 feat(engine): reintroduce per-message swipes with dedicated table`), and `git log -S"ADD COLUMN location_header"` is empty across all branches — the table was never born without it. Inferred: a DB that has `message_swipes` at all has the column, so no repair path was ever needed. I did not run a migration against a real old DB.
- **What an old Game's story log shows** (inferred from the pre-fix writer plus the read path): the header sits on the Message that came *after* the moving Narration — normally the next Action's player Input — and the moving Narration shows none. A stored `pending_location` left in an old Snapshot is also replayed onto the next Message added to that Game. Nothing in the render path can tell a pre-fix row from a post-fix one; there is no migration or reader-side normalisation.

## 7. What each option of ticket 03 would change, and the option-B data gap

| Option | Code changes | Data it needs | Present today? |
|---|---|---|---|
| **A.** Keep the header on the Swipe, point the Swipe at its **result** Snapshot | `MessageService::save_message_and_snapshot` (store the second pointer), `MessageService::switch_swipe` (restore the result Snapshot), `log_movement_completion`/`save_arriving_location` unchanged, plus ticket 01's rewind/result split so guided Retry keeps `S1` | a second pointer per Swipe; the post-engine Snapshot id must be captured where it is currently discarded | **Missing** (see below) |

**The option-B gap, concretely.** Ticket 03's option B is "derive the header from the Swipe's **result** Snapshot". Two things make that impossible with today's data:

1. **No result pointer.** `Swipe.snapshot_id` is set once, at the first save after the Message/Swipe is created — the `"pre-quantifier narration"` save — so it holds the state *before* the Quantifier and the movement (`docs/diataxis/explanation/storage_design.md` §Per-swipe state binding claims the opposite; see §8). The post-engine Snapshot (`"post-engine snapshot"`, the first state that knows the new room) is written by `persist_snapshot_or_err`, which returns `Result<(), PhaseError>` and throws the id away; nothing writes it onto the Swipe or Message. So a render has no way to ask "what room did this generation end in?".
2. **No "before" side.** Even with a result pointer, the "show it when the room differs from the room before" rule needs the previous room. Today the only ids on hand are the other Swipes' pre-Quantifier Snapshots, and those hold the *same* room for the generation that moved (the Input's `Sc` and the Narration's `S1` are both pre-turn). So a snapshot-diff render built on today's pointers would put the header on the *following* Message — the pre-fix bug — not on the moving Narration.

Also worth recording for the decision: **option B fixes the display only.** `MessageService::switch_swipe` restores the Swipe's `snapshot_id`, so unless option 01 also changes the restore target (or B derives the header from the *restored* state rather than the result Snapshot), the mismatch of §3 survives: the header would still name the room the generation arrived in while the switch puts the player back in the room it left. Option A is the only one of the three that changes the restore.

## 8. Contradictions to flag

- **`docs/diataxis/explanation/storage_design.md` §Per-swipe state binding** — "Each swipe keeps the Snapshot of the state that its own narration produced, so the text on screen and the world state always come from the same generation." **Contradicted** (known). The code sets the pointer at the pre-Quantifier save, so a Swipe keeps the state its generation *started* from. This is the root of the ticket-03 mismatch, and it is what makes option B's "result Snapshot" unavailable.
- **`docs/diataxis/reference/game_flow.md` §Movement Branch** — "The room a movement lands in is the location header of the Swipe whose generation moved the player." **Accurate after the ticket-15 fix** (work tree), **false at HEAD**. §Retry Flow ("Main retry restores the Snapshot of its anchor Message before generation") matches the code.
- **Ticket 08's premise** "`pending_location` remains only for the starting scenario's Narration" — accurate for the writers, but `MessageService::build_fresh_initial_state` can leave the value set in a persisted Snapshot (empty rendered scenario text), and the next Message then takes it; for a scenario-less World that next Message is the arrival Narration (inferred).
- **Ticket 08's premise** that the header must agree with the Snapshot a swipe switch restores — **the code does not do this**, and ticket 15's Answer already records it as deferred (option B of that ticket).
- **Subplan C** contradicts the shipped ticket-15 behaviour (§5) and cites a code layout that no longer exists.
- Nothing here contradicts `docs/specs/swipe_new.md` scenarios 9.2/9.8/10.8/22.5 or `docs/specs/actions.md` 1.14; those pin the header strings only, never the restored room.
