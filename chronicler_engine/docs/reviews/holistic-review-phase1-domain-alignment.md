# Phase 1: Domain Alignment — Findings

**Date:** 2026-05-09  
**Scope:** Map the game's conceptual model to the code module graph  
**Method:** Vocabulary extraction from docs, type inventory from `model/`, concept mapping from `engine/` and `narrative/`

---

## Executive Summary

The codebase has a **rich, well-documented domain** (interactive fiction + LLM narrative generation) but **significant vocabulary drift** between docs, model types, and engine concepts. The most impactful finding: three core types are **misnamed relative to their actual meaning**, which creates persistent confusion when reasoning about state mutations and trigger behavior.

**Severity:** The naming issues are **moderate** — they don't cause bugs, but they slow down reasoning and make the architecture harder to explain to new contributors.

## 3. Domain Friction Points (Ranked)

### 3.1 HIGH: `CharacterState` Is Misnamed and Misplaced

**Current:** `model::trigger::CharacterState` is `HashMap<String, NpcEncounterState>`.

**Problem:** The name implies "a single character's state." The actual meaning is "the player's encounter history with ALL NPCs." It lives in `trigger.rs` but tracks encounter data, not trigger definitions.

**Impact:** Every time someone reasons about "character state" they must mentally correct to "NPC encounter tracker." This is a tax on every engineer who touches trigger eval or action processing.

**Evidence:**
- `trigger_eval.rs` has functions like `increment_times_met`, `set_currently_meeting`, `is_trigger_fired` — these all operate on `CharacterState` but have nothing to do with trigger *definitions*.
- `test_support/fixtures.rs` sets `character_state: Default::default()` when creating test states, which is misleading — it's not a generic default, it's "no encounters yet."

**Recommendation:** Rename to `NpcRelationsState` or `EncounterTracker`. Move to `model::character.rs` or `model::state.rs`.

### 3.2 HIGH: `TriggerAction` Is Not an Action

**Current:** `model::trigger::TriggerAction` contains `name` + `narration_prompt`.

**Problem:** The name collides with `engine::action::Action` (player commands: Look, Talk, FreeAction, etc.). A `TriggerAction` is actually a **narration effect** — it tells the LLM what to narrate when a trigger fires.

**Impact:** Searching for "Action" in the codebase returns two completely unrelated concepts. This makes code navigation harder.

**Evidence:**
- `action_processing.rs` calls `trigger.action.narration_prompt` to build a prompt for the LLM.
- The struct has no behavior — it's pure data describing a narrative output.

**Recommendation:** Rename to `TriggerEffect` or `TriggerNarration`.

### 3.3 MEDIUM: `GenerationState` Is UI Input Buffer State

**Current:** `model::state::GenerationState` contains `input`, `cursor_position`, `scroll_offset`.

**Problem:** The name implies "the state of the LLM generation process." The actual meaning is "the player's input buffer and UI cursor while the generation UI is active." `GenerationStatus` (Idle/Generating/Error) is the real generation state.

**Impact:** Low but persistent confusion. `GeneratingGuard` mutates `generation.status` (a field inside `GenerationState`), which is two levels of nesting away from the concept it represents.

**Evidence:**
- `GenerationState` is only referenced by `NarrativeState` and tests.
- Its methods (`push_char`, `pop_char`, `clear_input`) are UI input methods, not generation control methods.

**Recommendation:** Rename to `GenerationInputState` or `InputBufferState`.

### 3.4 MEDIUM: `SceneState` Is Narrower Than "Scene"

**Current:** `model::state::SceneState` only holds `npcs_in_area: Vec<NpcCard>`.

**Problem:** "Scene" in narrative/docs means "the current situation" (room, NPCs, lighting, mood). `SceneState` only tracks NPC presence. The actual scene description is generated by the LLM and lives in `narrative.history`.

**Impact:** When docs say "scene quantification," they mean "determine who is in the scene." When code says `SceneState`, it means "who is in the area." These are close but not identical.

**Evidence:**
- `QuantifierResult` has `npcs` and `movement` — both are scene-relevant, but only `npcs` goes into `SceneState`.
- The quantifier is called "scene quantifier" in docs but its output is split between `MovementState` and `SceneState`.

**Recommendation:** Accept the narrow definition but document it explicitly. Or rename to `PresenceState` if broader scene concepts are added later.

### 3.5 MEDIUM: `NpcEvent` Types Live in `narrative::quantifier`

**Current:** `NpcEventType` (Entered/Left) and `NpcEvent` live in `narrative::quantifier::types`.

**Problem:** These are **engine state-transition events**, not quantifier-specific types. The quantifier produces `QuantifierResult` (who is present). The *engine* diffs previous vs current NPCs to produce `NpcEvent` enter/leave transitions.

**Impact:** `engine::action_processing` must import `crate::narrative::quantifier::NpcEvent` to apply state changes. This is a narrative → engine dependency that feels backwards.

**Evidence:**
- `quantifier/parser.rs::compute_npc_events` diffs two ID lists to produce events.
- `action_processing.rs::apply_npc_events` consumes these events to mutate `CharacterState`.
- Neither function has anything to do with LLM calls or quantifier prompts.

**Recommendation:** Move `NpcEvent`, `NpcEventType`, `NpcEventList` to `engine::action_processing` or `model::state`.

### 3.6 LOW: `create_dynamic_room` Lives in `engine::logic`

**Current:** `engine::logic::create_dynamic_room` is a factory for `model::map::Room`.

**Problem:** It is pure data construction — no engine logic involved. It takes a trigger string and description, returns a `Room`.

**Impact:** Minor. It works where it is, but it's not obviously findable.

**Evidence:**
- Function body: constructs a `Room` with generated ID, no side effects.
- Only called by `handle_movement`.

**Recommendation:** Move to `model::map::Room` as `Room::dynamic()` or keep as-is. Low priority.

## 5. Cross-Module Concept Ownership

### 5.1 Clean Ownership (Good)

```
WorldCard        → model::world       (owned, referenced by engine/narrative/server)
MapDef/Room      → model::map         (owned, referenced by engine/narrative)
NpcCard/PlayerCard → model::character (owned, referenced by engine/narrative/server)
Trigger          → model::trigger     (owned, evaluated by engine)
LogEntry/LogType → model::state       (owned, rendered by server)
```

### 5.2 Split Ownership (Problematic)

```
Character/NPC encounters:
  - Definition: model::character::NpcCard
  - Runtime tracking: model::trigger::CharacterState  ← wrong module
  - Evaluation: engine::trigger_eval
  - Mutation: engine::action_processing

Scene presence:
  - Static config: model::map::Room.npcs
  - Dynamic runtime: model::state::SceneState.npcs_in_area
  - LLM-derived inference: narrative::quantifier::QuantifierResult
  - Event computation: narrative::quantifier::NpcEventList  ← wrong module

Player command:
  - Text parsing: engine::parser
  - Enum: engine::action::Action
  - NO model counterpart — model is action-agnostic
```

## 6. Recommendations

### Do Now (Low Cost, High Clarity)

1. **Rename `CharacterState` → `NpcRelationsState`** and move to `model::character.rs` or `model::state.rs`.
2. **Rename `TriggerAction` → `TriggerEffect`** in `model::trigger.rs`.
3. **Move `NpcEvent` types** from `narrative::quantifier` to `engine::action_processing` or `model::state`.

### Do Later (When Touching Related Code)

4. **Rename `GenerationState` → `GenerationInputState`** or `InputBufferState`.
5. **Document `SceneState` explicitly** as "NPC presence state, not full scene description."
6. **Consider `Room::dynamic()` factory** instead of `engine::logic::create_dynamic_room`.

### Do Never (Accept the Overload)

7. **"Prompt"** — too ubiquitous to rename. Use qualified names (`quantifier_prompt`, `system_prompt_layer`) when ambiguous.
8. **"Action"** — domain-standard term. Distinguish by context (`player_action` vs `trigger_effect`).
