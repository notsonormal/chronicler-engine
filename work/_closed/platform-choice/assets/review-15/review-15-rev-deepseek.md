# Review 15: the design and the build decisions against standard practice (reviewer: rev-deepseek)

Scope: shape-at-a-glance, target design v2, sketch 25, sketch 24, tickets 05, 08, 09, 11, 12, 13, with checks of the
code at HEAD. Labels: **known** (read; path cited), **inferred**, **guessed**. No build or test was run. No repo file
was changed; this report is the only file written.

## 1. Verdict

The runtime design is mostly standard and sound. State per Swipe, a derived current state, an in-memory job
registry with a fencing check (the job id), a plan of ids for the background job, targeted record writes inside
one transaction, a read side for the views and typed hook outputs for the Agents are all well-known patterns, and
the spec justifies the unusual-looking parts (the active-Game pointer, memory-only busy, the two-step save). The
drift is around the design, not in it: (a) the build path puts nearly all behaviour change into one red branch,
on a justification that is a Q&A preference, not a requirement; (b) the main test net (tier 1) runs on a
hand-written in-memory storage fake that the build must extend with emulated transactions, where the standard is a
real SQLite `:memory:` database; (c) a set of custom rules, walkers and a test-count pin defend custom choices (the
in-job type ban, the call-count rule, the unit-test ban) more than they defend requirements. Trim those three and
the design is in a sensible state for a single-user, single-process app.

## 3. Standard or sensibly simple (no change)

- Full game state on each Swipe, current state derived (D-01, D-02): versioned state per revision; the same as Marinara. Removes replay, restore and heal code.
- Memory-only busy with a job registry, cancel handle and RAII cleanup (`JobWriter` `Drop`): standard for one process (E-01, R-92). No status row to heal.
- The job id check on each save: a fencing token. Small and correct against stop, reset and late answers.
- One plain mutex for all Games, never held across an LLM call (D-07): simplest correct lock; storage is already serialized (known: `Mutex<BackendKind>`, `storage/core.rs:18`).
- `JobPlan` of ids plus one runner, one `generate` (ticket 05): transaction script / command; removes the known duplication (research 12 §2c).
- Option S (straight code) over a state machine (ticket 05): measured and simpler.
- `SavedText` token: idiomatic Rust typestate, under 20 lines (guessed).
- Narrow targeted record writes in one transaction per save unit: unit of work without a framework.
- Keep the `Backend` enum and methods on `Storage`; no port traits with one adapter; CRUD services untouched (ticket 11 R1, R2, R5).
- `CurrentGame` axum extractor; the active-Game pointer itself is a spec requirement (clean-spec §2, R-79, R-81), not drift.
- Read side (`GameViewQuery`) separate from writes: CQRS-lite.
- Agent hooks with one typed output per hook; only the two hooks with Agents are built (D-34): a plugin registry, justified by the owner's stated wish to support more Agents (sketch 24 §0).
- No `loom`/`shuttle`; deterministic race tests with a holdable fake (ticket 12): proportionate.
- One crate, docs rewritten in place, generated indexes kept (ticket 13 §4, §5).
- P1 (`ActiveGame`) and P3 (`SwipeState` inside `GameState`) are textbook preparatory refactors.

## 4. Top three changes before the build plan is written

1. **Split the core step.** Move the dock record, the failure line on `games` and the notice removal into a green preparation slice on today's pipeline, and the narrow view reads into another. Then strangle `ActionPipeline` per request kind with `job.rs`, behind the same handlers. Keep one larger step only for the Snapshot → `SwipeState` record switch, with the cost of a dual-write adapter stated, not inferred away.
2. **Run tier 1 on real SQLite.** Make SQLite `:memory:` the tier-1 default, since tier 1 is now the main net for transactions and races. Then decide if the new records need an in-memory arm, a copy-and-swap `Tx` and a second failure-injection mechanism at all.
3. **Cut the rules that guard rules.** Drop guardrail rules 7, 8, 10 and 17 and the unit-test count pin; replace rules 7 and 8 with one R-59 scenario; express rule 3 (and 2 if cheap) as a capability type. Allow plain unit tests on pure domain functions. This keeps the enforcement that maps to real failure classes (1, 6, 13, 18, the compiler rows) and removes most of the custom tooling.
