# Decide the fate of the dead diagnostic benchmark

Type: grilling (HITL)
Status: resolved
Blocked by: —
Claimed by: pi session (wayfinder run)
Resolved: 2026-10-06

## Question

`scripts/diagnostic_benchmark.py` — and the `build.py --diagnostic-benchmark` gate flag that runs
it — have no data source. `run_benchmark()` shells `cargo test --test diagnostic_benchmark`, and
that target does not exist:

```
$ cargo test --test diagnostic_benchmark --no-run
error: no test target named `diagnostic_benchmark` in default-run packages
```

`fe09985a` decomposed `tests/diagnostic_benchmark.rs` into `tests/diagnostic.rs` plus a
`diagnostic/` directory, renaming the cargo target to `diagnostic`; the script was never updated.
`d34c8785` then removed the `diagnostic` target with the test-tree reorganization. The old entry
points (`DefaultGameService`, `GameServiceContext`, `make_test_context`) are gone from `src/`, so
the ~950 lines of `scenarios.rs` + `backends.rs` are a rewrite, not a restore.

Surfaced by [Record contention and effect size in benchmark reports](08-benchmark-contention-effect-size.md),
which built the report fields but cannot exercise them end to end. `--diagnostic-benchmark` exits 1
before writing anything.

What should happen to the diagnostic benchmark?

- **Rebuild** a `diagnostic_benchmark` target so the report runs. Which scenarios survive the
  pipeline rewrite, and what is the smallest suite that still measures diagnostic signal quality?
- **Drop** it: remove `scripts/diagnostic_benchmark.py`, its tests, and the `--diagnostic-benchmark`
  flag.
- **Park** it: keep the script, mark it unrunnable, and leave the flag out of the gate help.

## Context

## Done when

## Answer

Resolved 2026-10-06. The benchmark is **deleted** — not rebuilt, not parked.

**Why the ticket's rebuild option lost.** The suite's numbers were authored, not measured. Each
scenario scored itself with a hand-written mapping from a string property to a number:

```rust
error_specificity: if error_msg.contains("401") { 10 } else { 2 },
```

(`tests/integration/diagnostic/scenarios.rs` at `d34c8785^`; the same shape in all twelve
scenarios.) The scenario's real content is the assertion beneath it — `assert!(error_msg.contains("401"))`
— which measures the engine, while the score encodes the author's opinion of that boolean. No field
in the schema recorded a duration, so the report fields built in
[Record contention and effect size in benchmark reports](08-benchmark-contention-effect-size.md)
(`--repeat` spread, `--compare` effect size) operated on constants and were always zero. The
advertised loop — baseline, fix, compare — could not work. Rebuilding would recreate ~950 lines of
fakes and harness to regenerate hand-typed weights; parking would keep 788 lines of dead code and
the same trap. The one version that would earn a rebuild, a suite scored by an independent judge
rather than by hand, is a different and larger project, and is out of scope.

**What was removed** (applied in this session, per the map's execution override):

- `scripts/diagnostic_benchmark.py` — deleted. 308 lines committed; the worktree copy was 536,
  because ticket 08's ~228 lines had never been committed, and they went with it.
- `scripts/tests/test_diagnostic_benchmark.py` — deleted. It was **untracked**: ticket 08's 17 unit
  tests had never been committed.
- `build.py` — the `--diagnostic-benchmark` flag, its `_GATE_ONLY_FLAGS` entry, the
  `run_diagnostic()` handler, its dispatch branch, and the flag's mention in the module docstring's
  lock-coverage note.
- `scripts/tests/test_build_cli.py` — three `diagnostic_benchmark=False` argument stubs.
- `AGENTS.md` structure index — regenerated by `scripts/generate_structure_index.py`, not hand-edited.

**Verification** (2026-10-06): `python build.py py-tests` → 285 tests, OK (302 before; the deleted 17
account for the drop). `python build.py docstrings` → 0 errors. A repo-wide grep for
`diagnostic_benchmark` / `--diagnostic-benchmark` outside `.scratch`, `tmp`, `target` and `logs`
returns nothing. `tmp/diagnostics` never existed.

**Correction to "isn't called".** Two things did call it: the `--diagnostic-benchmark` mode, and the
gate's `py-tests` step, which ran the script's 17 unit tests on every full gate. Both ties are gone.
The cargo target it shelled out to never existed, and no CI, doc or other test referenced it.

**F28/F29 are re-dispositioned to dropped.** Ticket 08 built them into this script, and the map
recorded F28 as "absorbed into the benchmark fields". The script was that mechanism's only host, and
the fields had no producer that varied, so they never fired. The rule stays readable in ticket 08's
answer. `build.py`'s own step timings and its history journal (`logs/build_history.txt`) are the
place a future effort could give it a live host; recorded out of scope on the map, not graduated.

**The twelve signal assertions are recorded out of scope.** The durable part of the suite was a
checklist that the user-facing error names its cause, across six categories (LLM, Quantifier,
Navigation, Narrative, Triggers, State). No test asserts that today — `tests/http/failure_display.rs`
only asserts the raw error is rendered. Recovering it is Chronicler Engine testing, not agent-workflow
friction; the scenarios are recoverable from `tests/integration/diagnostic/scenarios.rs` at `d34c8785^`.
